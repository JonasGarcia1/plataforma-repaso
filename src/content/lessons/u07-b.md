## Concepto

Concurrencia significa gestionar tareas que se superponen; paralelismo significa ejecutarlas simultáneamente. Crear más hilos no garantiza terminar antes. Compartir estado mutable introduce carreras: el resultado depende del entrelazado de operaciones.

`stock--` incluye leer, restar y escribir. Dos hilos pueden leer el mismo valor y perder una actualización. `volatile` ofrece visibilidad y orden de memoria para ese campo, pero no convierte una secuencia compuesta en atómica. `synchronized` usa un monitor para exclusión mutua y relaciones de visibilidad entre accesos correctamente coordinados.

Un executor separa tareas de administración de hilos. Elegí tamaño y política de cola según el trabajo y cerralo cuando termine su propietario. Para servicios de larga vida, además definí límites de cola y rechazo; una cola ilimitada puede acumular más trabajo del que el servicio puede procesar.

## Ejemplo

Java 21 ejecutable como `Reservas.java`:

```java
import java.util.concurrent.*;
class Reservas {
    static class Inventario {
        private int stock = 1;
        synchronized boolean reservar() {
            if (stock == 0) return false;
            stock--;
            return true;
        }
    }
    public static void main(String[] args) throws Exception {
        var inventario = new Inventario();
        try (var executor = Executors.newFixedThreadPool(2)) {
            Future<Boolean> a = executor.submit(inventario::reservar);
            Future<Boolean> b = executor.submit(inventario::reservar);
            System.out.println(a.get() + " / " + b.get());
        }
    }
}
```

Exactamente una reserva será verdadera. El orden de los resultados no está garantizado. El bloque protegido incluye tanto la comprobación como la modificación.

## En entrevista

**Respuesta breve:** protejo invariantes completas; visibilidad no equivale a atomicidad y prefiero reducir el estado compartido.

**Respuesta ampliada:** puedo usar atómicos para contadores simples, pero un inventario con varias reglas puede necesitar una sección crítica o una transacción. Un bloqueo Java solo coordina hilos de ese proceso; no resuelve reservas desde otras instancias del servicio.

## Error frecuente

Sincronizar escritores pero dejar lectores sin coordinación y esperar visibilidad garantizada. Todos los accesos que integran la política deben respetar el mismo mecanismo.

## Práctica

¿Alcanzaría con declarar `volatile int stock` en el ejemplo y quitar synchronized? Explicá un entrelazado incorrecto.

### Pista

Ambos hilos pueden pasar la condición antes de que alguno descuente.

### Solución

No alcanza: ambos pueden leer stock igual a uno y aceptar. Aunque cada lectura vea datos recientes, no hay exclusión de la operación completa. Mantené el monitor o diseñá una operación compare-and-set que haga validación y cambio juntos.

## Profundización

Los deadlocks aparecen cuando tareas esperan recursos retenidos entre sí. Un orden consistente de adquisición y secciones críticas pequeñas ayuda. No retengas bloqueos durante llamadas lentas si el diseño permite separarlas de la modificación protegida.
