# Contratos de eventos que evolucionan

## Concepto

Un evento compartido tiene tres capas: el formato de bytes, el schema que describe su estructura y el contrato que explica qué significan los campos y cómo cambian. JSON, Avro y Protobuf son formatos posibles. Avro y Protobuf suelen hacer explícitos los tipos y el schema, mientras que JSON puede circular con o sin validación central. Ningún serializador decide por sí solo si un cambio conserva el significado del negocio.

Un Schema Registry almacena versiones de schemas y aplica una política de compatibilidad al registrar cambios. La política elegida define qué combinaciones de productores y consumidores pueden convivir. La compatibilidad hacia atrás permite que un consumidor nuevo lea datos antiguos; la compatibilidad hacia adelante permite que un consumidor antiguo tolere datos nuevos. “Full” combina ambas direcciones según las reglas del registro. El nombre exacto y el alcance de esas reglas dependen del registry y su configuración.

Antes de publicar un cambio, identificá quién produce y quién consume el evento, incluidas aplicaciones que despliegan en otro calendario. Un cambio aditivo puede ser compatible si el campo nuevo es opcional y tiene un valor predeterminado adecuado. Eliminar un campo, volverlo obligatorio, cambiar unidades o reinterpretar su significado puede romper consumidores aunque la validación estructural pase.

## Ejemplo

Un evento `OrderCreated` agrega `salesChannel`. El contrato establece que consumidores antiguos pueden ignorarlo y consumidores nuevos aceptan que falte en registros anteriores. Con Avro, el campo puede declararse con `null` y un default; en JSON, un contrato equivalente debe acordar opcionalidad y validación. En ambos casos, primero se publica compatibilidad y se comprueba la lectura en ambas versiones.

```json
{
  "type": "record",
  "name": "OrderCreated",
  "fields": [
    {"name": "orderId", "type": "string"},
    {"name": "salesChannel", "type": ["null", "string"], "default": null}
  ]
}
```

Este fragmento es un schema Avro ilustrativo; la política efectiva la determina el registry configurado.

## En entrevista

**Pregunta:** ¿Cómo desplegarías un cambio de esquema de eventos sin romper consumidores activos?

**Breve:** Mantendría compatibilidad entre las versiones que conviven: primero desplegaría consumidores tolerantes y después productores que agreguen el campo.

**Ampliada:** Validaría el esquema en CI y definiría compatibilidad hacia atrás o hacia adelante según el despliegue. Si se renombra un campo, publicaría una versión nueva o haría una transición donde consumidores acepten ambos formatos antes de retirar el anterior.
## Error frecuente

Cambiar `amount` de pesos a centavos manteniendo el mismo nombre y tipo. El registro puede aceptar el schema, pero el significado cambió y el consumidor calculará mal. También es riesgoso renombrar campos como si fueran cambios puramente cosméticos.

## Práctica

Diseñá una evolución compatible de `OrderCreated` para agregar un canal de venta. Indicá qué versiones leen cada payload, qué política elegirías y cómo retirarías el campo anterior si más adelante debe reemplazarse.

### Pista

Enumerá productor actual, productor nuevo, consumidor actual y consumidor nuevo. Para cada combinación, anotá si puede serializar y leer el evento.

### Solución

Agregá el campo como opcional con default documentado, registrá el schema bajo una política compatible y probá ambos sentidos de lectura con payloads representativos. Desplegá consumidores capaces de tolerar el campo antes de exigirlo a los productores. Si el significado cambia, publicá un campo nuevo y migrá por etapas; no reutilices silenciosamente el campo viejo.

## Profundización

El contrato también necesita dueño, identificador de evento, versión o estrategia equivalente, política de retención y ejemplos válidos. Evitá incluir datos personales innecesarios: un evento durable puede replicarse y permanecer disponible durante la retención. Para cambios incompatibles, una nueva versión de topic puede hacer explícito el corte, aunque aumenta el trabajo de migración.

Para ver una configuración aplicada de serializadores JSON en el cliente, consultá [configuración JSON de producer y consumer](/leccion/kafka-json-configuration); podés hacerlo después de esta explicación, sin que sea un requisito.
