# Contratos de eventos que evolucionan

## Concepto

JSON, Avro y Protobuf son formatos de representación; el contrato define campos, significado, opcionalidad y evolución. Un Schema Registry almacena versiones y puede verificar reglas de compatibilidad antes de aceptar un cambio. Eso reduce sorpresas, pero no reemplaza pruebas entre productores y consumidores.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

Compatibilidad hacia atrás permite que un consumidor nuevo lea mensajes antiguos; hacia adelante permite que un consumidor antiguo tolere mensajes nuevos. Agregar un campo opcional suele ser más seguro que renombrar o cambiar el significado de uno existente. La semántica también debe versionarse.

```json
// Fragmento de schema Avro: agregar campos opcionales facilita la compatibilidad.
{"type":"record","name":"OrderCreated","fields":[
  {"name":"orderId","type":"string"},
  {"name":"canalDeVenta","type":["null","string"],"default":null}
]}
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

Una respuesta breve sería: “schemas, formatos y compatibilidad se usa para tomar una decisión explícita y verificable; primero aclaro el contrato, luego indico el costo y finalmente describo qué haría ante un fallo o un dato inesperado”. Una respuesta ampliada debe sumar un ejemplo concreto, una alternativa descartada y el límite que evita prometer garantías que la herramienta no ofrece.

## Error frecuente

Cambiar un campo de importe de pesos a centavos manteniendo el mismo nombre y tipo. El schema puede aceptar la forma, pero el contrato de negocio se rompe. También es erróneo publicar clases internas como evento público sin una frontera.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Definí evento, versionado y consumidores antes de elegir serializador. Incluí una key estable, un identificador de evento, fecha y solo datos necesarios para el caso de uso.

Consigna: Evolucioná OrderCreated para agregar canalDeVenta sin romper consumidores existentes.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Agregá un campo opcional con valor por defecto documentado, mantené el campo anterior y verificá compatibilidad en el registro de schemas. Publicá ejemplos y medí consumidores antes de hacer obligatorio el nuevo dato.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

Los contratos de eventos son productos compartidos. Compatibilidad técnica y significado de negocio deben revisarse juntos.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
