# Stack, heap y referencias

## Concepto

La pila de ejecución contiene marcos de métodos y referencias locales; el heap aloja objetos administrados por la JVM. Son modelos para razonar, no una promesa de ubicación exacta para cada optimización de la JVM. Una variable de referencia se copia al pasarla como argumento, por eso Java sigue pasando argumentos por valor.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

Si un método modifica un objeto recibido, ambos llamadores ven el mismo objeto porque conservan referencias al mismo estado. Si reasigna su parámetro a otro objeto, solo cambia su copia local. Esta distinción explica muchos errores al intentar “devolver” una referencia mediante un parámetro.

```java
static void cambiar(Pedido pedido) {
  pedido.agregarLinea("SKU-1"); // el llamador observa esta mutación
  pedido = new Pedido();        // solo cambia la copia local de la referencia
}
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

Una respuesta breve sería: “alcance, objetos y paso por valor se usa para tomar una decisión explícita y verificable; primero aclaro el contrato, luego indico el costo y finalmente describo qué haría ante un fallo o un dato inesperado”. Una respuesta ampliada debe sumar un ejemplo concreto, una alternativa descartada y el límite que evita prometer garantías que la herramienta no ofrece.

## Error frecuente

Confundir la pila de memoria con java.util.Stack, o suponer que null libera un objeto inmediatamente. El recolector libera objetos inalcanzables cuando decide ejecutarse; no es una instrucción de liberación manual.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Nombrá el dueño de cada objeto mutable y acotá su alcance. Cuanto menos tiempo viva una referencia, más simple es entender quién puede cambiarla y por qué sigue alcanzable.

Consigna: Explicá qué ve el llamador cuando un método agrega una línea a un pedido y luego reasigna el parámetro pedido.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

El agregado se observa porque ambos apuntan al mismo objeto. La reasignación solo altera la variable local del método. Para cambiar el resultado del llamador, devolvé explícitamente el nuevo objeto o mutá una operación acordada.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

Las fugas en Java no son memoria “sin GC”: son objetos que el programa todavía puede alcanzar por cachés, listeners, colecciones estáticas o tareas largas.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
