## Concepto

MVC separa modelo, vista y controlador. En una API con Spring MVC, el controlador traduce HTTP a una llamada de aplicación; el servicio ejecuta el caso de uso y un convertidor transforma el resultado en JSON. No hay que meter SQL, reglas de stock y envío de emails en el mismo controller.

@RequestBody deserializa el cuerpo. @Valid activa la validación de restricciones declaradas en el DTO cuando se integra Bean Validation. Validar un campo no sustituye las reglas de dominio: un número positivo puede superar el stock disponible.

Los errores previsibles necesitan contratos consistentes. @RestControllerAdvice centraliza traducciones de excepciones; ProblemDetail permite describir problemas HTTP con campos estándares y extensiones controladas. El cliente necesita una explicación útil, no un stack trace.

## Ejemplo

Fragmento parcial Java 21 / Boot 3 con starter web y validation; servicio omitido:

```java
record CrearPedidoRequest(
    @NotBlank String sku,
    @Min(1) int quantity) {}

@RestController
@RequestMapping("/api/orders")
class PedidoController {
    private final PedidoService service;
    PedidoController(PedidoService service) {
        this.service = service;
    }

    @PostMapping
    ResponseEntity<PedidoDto> crear(
            @Valid @RequestBody CrearPedidoRequest request) {
        PedidoDto pedido = service.crear(request);
        return ResponseEntity.created(
            URI.create("/api/orders/" + pedido.id())
        ).body(pedido);
    }
}
```

El servicio determina el identificador; el controller comunica la ubicación del recurso nuevo.

## En entrevista

**Pregunta:** ¿Qué responsabilidades separarías entre controller, service y repository?

**Breve:** controller maneja el contrato HTTP; service coordina negocio; repository encapsula acceso a datos.

**Ampliada:** distinguiría 400 por datos inválidos, 404 por pedido inexistente y 409 por conflicto de estado. Una caída imprevista devuelve 500 y un identificador de correlación, sin detalles internos.
## Error frecuente

Atrapar Exception y devolver siempre null o 200. Esto oculta fallos y obliga al cliente a interpretar respuestas ambiguas.

## Práctica

El pedido 42 existe, pero ya fue enviado. ¿Cómo responderías a una solicitud de cancelación que el negocio prohíbe?

### Pista

El recurso existe y la estructura de la petición es válida.

### Solución

El caso de uso lanza una excepción específica de conflicto. El advice la transforma en 409 con título y detalle controlados. Testeá también cancelación válida y pedido inexistente para no mezclar los escenarios.
