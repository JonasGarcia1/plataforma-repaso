# Kafka Streams, seguridad y capacidad

## Concepto

Kafka Streams permite transformar, agrupar y unir registros manteniendo estado local respaldado por topics internos. Las ventanas definen cómo se agrupan eventos por tiempo; deben incluir política para eventos tardíos y retención. No es necesario adoptarlo para cada consumer: una proyección simple puede ser más clara.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

TLS cifra tráfico, SASL autentica clientes y ACL autoriza acciones sobre topics o grupos. Son controles complementarios. El lag muestra diferencia de offsets, pero necesita contexto: una subida breve durante un pico no equivale a un consumer detenido o a una capacidad insuficiente sostenida.

```java
// Fragmento Kafka Streams: una ventana define cómo agrupar eventos por tiempo.
builder.stream("orders.created")
    .groupByKey()
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5)))
    .count(Materialized.as("pedidos-por-ventana"));
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

Una respuesta breve sería: “estado, permisos, lag y límites se usa para tomar una decisión explícita y verificable; primero aclaro el contrato, luego indico el costo y finalmente describo qué haría ante un fallo o un dato inesperado”. Una respuesta ampliada debe sumar un ejemplo concreto, una alternativa descartada y el límite que evita prometer garantías que la herramienta no ofrece.

## Error frecuente

Dar permisos de administrador a todos los servicios, o escalar consumers por encima de las particiones esperando más paralelismo. También es un error tratar lag como un número aislado sin tasa de llegada y tiempo de procesamiento.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Definí quién puede leer, escribir y administrar cada recurso. Para capacidad, medí producción, consumo, tamaño de mensajes, particiones, lag y tiempo de recuperación antes de cambiar la topología.

Consigna: Explicá cómo proteger y monitorear un consumer que mantiene una agregación por pedido.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Usá credenciales por servicio, TLS cuando corresponda y ACLs mínimas para topic y group. Medí lag y tasa de proceso; si el cuello persiste, revisá particiones, procesamiento y recursos antes de sumar instancias.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

Operar Kafka es entender contratos, seguridad y flujo. Las métricas guían la capacidad; las ACLs y el cifrado limitan quién puede afectar ese flujo.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
