# SQL de entrevista y diagnóstico

## Concepto

El diseño de una tabla es una primera línea de defensa. Una clave primaria identifica, una foreign key preserva relaciones y una restricción UNIQUE evita duplicados cuando esa regla realmente pertenece a los datos. Normalizar reduce anomalías, pero no prohíbe crear una proyección de lectura cuando una consulta real lo justifica.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

EXPLAIN no optimiza una consulta: muestra el plan elegido. Se comparan filas estimadas y reales, tipo de acceso, joins y costo. Un índice compuesto ayuda cuando su prefijo responde al filtro y al orden; agregar índices sin observar escrituras puede empeorar inserciones y actualizaciones.

```sql
-- Fragmento SQL: el esquema y los nombres dependen del dominio.
CREATE TABLE linea_pedido (
  pedido_id BIGINT NOT NULL REFERENCES pedido(id),
  producto_id BIGINT NOT NULL,
  cantidad INTEGER NOT NULL CHECK (cantidad > 0),
  PRIMARY KEY (pedido_id, producto_id)
);
CREATE INDEX idx_pedido_cliente_fecha ON pedido(cliente_id, creado_en);
EXPLAIN ANALYZE SELECT * FROM pedido WHERE cliente_id = 7 ORDER BY creado_en DESC;
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

**Pregunta:** ¿Cómo combinarías normalización, constraints e índices al diseñar una tabla?

**Ampliada:** Modelaría primero entidades y relaciones, luego expresaría reglas como claves foráneas y unicidad en la base. Agregaría un índice compuesto según filtros y orden reales de las consultas, y comprobaría el plan de ejecución con datos representativos. Un índice innecesario ralentiza escrituras, así que mediría antes de conservarlo.
## Error frecuente

Crear un índice por cada columna después de ver una consulta lenta. También es peligroso resolver un deadlock con reintentos infinitos: primero se revisa el orden de bloqueo, el tamaño de la transacción y la consulta que mantiene recursos.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Explicá qué pregunta responde el índice, qué campos filtra y cómo verificarías el plan en un entorno representativo. La base de datos decide con estadísticas, no por la intención declarada en Java.

Consigna: Diseñá pedido y línea_pedido con claves, cantidad positiva y una consulta por cliente y fecha. Explicá qué índice probarías.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Definí primero PK y FK. Después usá CHECK para cantidad, UNIQUE solo para una regla de unicidad real y ejecutá EXPLAIN ANALYZE sobre la consulta. El índice puede comenzar por cliente_id si es el filtro más selectivo del acceso esperado.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

Un deadlock no demuestra que la base esté rota: dos transacciones pueden tomar recursos en orden distinto. Reducí el alcance, bloqueá en un orden consistente y aplicá un reintento limitado solo cuando el caso sea seguro.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
