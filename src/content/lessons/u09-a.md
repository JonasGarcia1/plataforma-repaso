## Concepto

HTTP define cómo se intercambian solicitudes y respuestas. REST es un estilo arquitectónico: identificamos recursos, usamos una interfaz uniforme y mantenemos las solicitudes independientes del contexto de sesión del servidor. Una API que envía JSON no es automáticamente REST.

GET consulta; POST procesa o crea; PUT reemplaza el estado de un recurso conocido; PATCH modifica parcialmente; DELETE elimina. GET es seguro: el cliente no solicita una modificación. PUT y DELETE son idempotentes: repetirlos tiene el mismo efecto pretendido que ejecutarlos una vez, aunque cambien las respuestas. PATCH depende de su operación.

Los estados comunican resultados: 200 éxito con representación, 201 creación, 204 éxito sin cuerpo, 400 petición inválida, 401 falta autenticación válida, 403 acceso denegado, 404 recurso ausente, 409 conflicto y 500 fallo inesperado. Las familias 3xx redirigen; 4xx describen problemas de la petición; 5xx problemas del servidor. Un error no se convierte en éxito devolviendo 200.

## Ejemplo

Contrato HTTP ilustrativo, independiente del lenguaje:

```http
POST /api/orders HTTP/1.1
Content-Type: application/json
Accept: application/json

{"sku":"BOOK-42","quantity":1}

HTTP/1.1 201 Created
Location: /api/orders/42
Content-Type: application/json

{"id":42,"status":"CREATED"}
```

Content-Type describe lo enviado; Accept expresa lo que el cliente puede recibir. Authorization transporta credenciales y no debe aparecer en registros.

## En entrevista

**Breve:** idempotencia significa conservar el efecto final ante repeticiones, no devolver siempre el mismo código.

**Ampliada:** después de un timeout podría haberse creado el pedido. Reintentar POST sin una estrategia puede duplicarlo. Una clave de idempotencia debe asociarse al resultado y al contenido de la solicitud de manera persistente y atómica.

## Error frecuente

Confundir 401 con 403, o asumir que DELETE deja de ser idempotente cuando la segunda llamada devuelve 404.

## Práctica

Elegí método y respuesta para consultar un pedido, reemplazar su dirección y crear otro. Explicá qué reintento exige cuidado.

### Pista

Separá recurso conocido, nueva identidad y efecto repetido.

### Solución

GET /orders/42 → 200 o 404; PUT /orders/42/address → 200 o 204; POST /orders → 201 y Location. Repetir el POST necesita deduplicación si no queremos dos pedidos.

## Profundización

Con ETag e If-Match el cliente puede condicionar una actualización a una versión conocida; una precondición fallida puede devolver 412. Esto evita sobrescrituras silenciosas y complementa el control de concurrencia de la base de datos.
