## Concepto

@Transactional delimita una unidad de trabajo gestionada por Spring. En el modo habitual basado en proxies, una llamada externa atraviesa el proxy; una llamada de un método a otro dentro del mismo objeto puede no activar la anotación del segundo método.

Por defecto, Spring revierte ante RuntimeException y Error; las checked exceptions necesitan una política explícita si también deben revertir. readOnly comunica intención y permite optimizaciones, pero no constituye por sí mismo una barrera de seguridad contra escrituras.

El locking optimista detecta modificaciones concurrentes mediante una versión. El pesimista bloquea datos durante una operación y puede reducir concurrencia o generar deadlocks. Elegimos según contención, duración y regla de negocio.

## Ejemplo

Fragmento parcial Java 21 / Jakarta Persistence y Spring; entidad y repositorio existentes:

```java
@Entity
class Producto {
    @Id Long id;
    @Version Long version;
    int stock;

    void reservar() {
        if (stock <= 0) throw new IllegalStateException("Sin stock");
        stock--;
    }
}

@Transactional
public void reservar(long id) {
    Producto producto = productos.findById(id).orElseThrow();
    producto.reservar(); // Dirty checking al sincronizar.
}
```

Si otro proceso actualiza la misma versión primero, la escritura debe fallar con un conflicto optimista. La aplicación decide si reintenta tras volver a leer o informa conflicto.

## En entrevista

**Pregunta:** ¿Qué limita `@Transactional` y cómo ayuda `@Version`?

**Breve:** la transacción protege cambios relacionados; @Version detecta actualizaciones perdidas.

**Ampliada:** mantendría transacciones cortas y evitaría llamadas remotas dentro de ellas. Reintentaría solo operaciones seguras, con límites, y volvería a evaluar invariantes en cada intento.
## Error frecuente

Atrapar una excepción y devolver éxito tras haber marcado la transacción para rollback. Otro error es suponer que la anotación cubre también servicios remotos.

## Práctica

Dos transacciones leen producto con versión 5 y stock 1. Ambas reservan. Explicá el resultado con @Version y cómo informar al segundo comprador.

### Pista

La actualización usa identidad y versión esperada.

### Solución

Una confirma y avanza la versión. La otra detecta que la versión original ya no coincide y revierte. Se puede releer y responder sin stock; no se debe reintentar el descuento ciegamente.

## Profundización

H2 es útil para aprender y para algunas pruebas, pero sus tipos, funciones, locking y planes no son idénticos a PostgreSQL u Oracle. Los modos de compatibilidad no garantizan equivalencia. Probá las consultas críticas contra el motor real en un entorno aislado.
