## Concepto

JPA, actualmente Jakarta Persistence, define una API y reglas para persistencia de objetos. Hibernate es una implementación. Spring Data JPA construye repositorios sobre esa API y reduce código repetitivo. Son capas complementarias, no tres nombres del mismo producto.

Una entidad tiene identidad persistente. @Id identifica su clave y las relaciones representan cardinalidades. En una relación bidireccional hay un lado propietario que determina la actualización de la asociación y un lado inverso indicado con mappedBy.

Fetch controla cómo se obtiene una relación; cascade propaga operaciones como persist o remove. Son decisiones independientes. EAGER no promete un único JOIN ni evita N+1. LAZY permite diferir carga, con límites según proveedor y contexto.

## Ejemplo

Fragmento parcial Java 21 / Jakarta Persistence; imports, constructores y accesores omitidos:

```java
@Entity
class LineaPedido {
    @Id @GeneratedValue
    Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "pedido_id")
    Pedido pedido; // Propietario: contiene la FK.
}

@Entity
class Pedido {
    @Id @GeneratedValue
    Long id;

    @OneToMany(mappedBy = "pedido", cascade = CascadeType.PERSIST)
    List<LineaPedido> lineas = new ArrayList<>();

    void agregar(LineaPedido linea) {
        lineas.add(linea);
        linea.pedido = this; // Mantener ambos lados.
    }
}
```

Agregar solo a la colección inversa no garantiza actualizar la clave foránea. La base sigue siendo la autoridad de integridad.

## En entrevista

**Pregunta:** ¿Qué papel cumplen JPA, Hibernate y Spring Data JPA?

**Breve:** JPA especifica, Hibernate implementa y Spring Data simplifica repositorios.

**Ampliada:** explicaría la propiedad de la relación, la estrategia de carga y qué operaciones deben propagarse. No agregaría CascadeType.ALL sin evaluar eliminaciones.
## Error frecuente

Usar cascada REMOVE desde un pedido hacia un cliente compartido. Borrar un pedido no debe borrar al cliente y afectar otros pedidos.

## Práctica

Un pedido tiene varias líneas exclusivas, pero pertenece a un cliente compartido. ¿Dónde considerarías orphanRemoval y dónde evitarías REMOVE?

### Pista

Preguntá qué objeto tiene un ciclo de vida dependiente del otro.

### Solución

orphanRemoval puede encajar en líneas que desaparecen al retirarlas del pedido. Evitaría REMOVE hacia Cliente. Verificaría restricciones y comportamiento en pruebas de persistencia antes de elegir la configuración definitiva.

## Profundización

El contexto de persistencia mantiene entidades gestionadas y detecta cambios. Una entidad detached ya no se sincroniza automáticamente. equals/hashCode requiere cuidado con identificadores generados y proxies; no incluyas colecciones de relaciones en métodos automáticos de Lombok.
