## Concepto

Un pipeline automatiza verificaciones y entrega artefactos reproducibles. Una secuencia habitual compila, ejecuta pruebas, analiza calidad y dependencias, empaqueta y despliega con controles del entorno. Las credenciales se gestionan fuera del repositorio; un pull request debe mostrar comportamiento y evidencia de validación.

SonarQube y herramientas similares detectan problemas o calculan métricas. Sus resultados necesitan interpretación: un umbral de cobertura no prueba que estén protegidas las reglas importantes. Las migraciones de base requieren compatibilidad con versiones que conviven durante un despliegue.

Spring Batch organiza procesamiento por lotes. Un Job contiene Steps; un step por chunks lee, transforma y escribe grupos dentro de límites transaccionales. JobRepository conserva metadatos para ejecución y reinicio. Una ejecución fallida no implica comenzar todo de cero.

## Ejemplo

Fragmento parcial Java 21 / Spring Batch 5 compatible con Boot 3; beans reader, processor, writer, JobRepository y transaction manager ya configurados:

```java
@Bean
Step importar(JobRepository repository,
              PlatformTransactionManager tx,
              ItemReader<Fila> reader,
              ItemProcessor<Fila, Pedido> processor,
              ItemWriter<Pedido> writer) {
    return new StepBuilder("importar", repository)
        .<Fila, Pedido>chunk(100, tx)
        .reader(reader)
        .processor(processor)
        .writer(writer)
        .build();
}
```

Cada chunk confirma hasta cien elementos. El tamaño afecta memoria, rendimiento y cantidad de trabajo repetido si ocurre un fallo.

## En entrevista

**Pregunta:** ¿Qué etapas pondrías en un pipeline de CI/CD y qué aporta Spring Batch?

**Breve:** un pipeline valida y entrega cambios; Batch procesa trabajo acotado con estado y posibilidad de reinicio.

**Ampliada:** distinguiría JobInstance mediante nombre y parámetros identificadores, de cada JobExecution. Diseñaría lectores reiniciables, checkpoints y escrituras idempotentes según los efectos externos.
## Error frecuente

Suponer que reiniciar evita todo duplicado o usar un parámetro de fecha aleatorio en cada intento y creer que seguimos la misma instancia lógica del job.

## Práctica

Un archivo contiene 250 registros y usamos chunks de 100. El proceso falla al escribir el tercer chunk. ¿Qué se confirma y qué revisarías antes de reiniciar?

### Pista

El límite transaccional es el chunk, no necesariamente todo el archivo.

### Solución

Los primeros 200 pueden estar confirmados; el tercero debería revertirse si su escritura es transaccional. Verificar checkpoint, parámetros y comportamiento de efectos externos. Una llamada HTTP hecha antes del fallo no se revierte con la transacción de base.

## Profundización

Diferenciá skip de retry: saltar un registro requiere una política de negocio y auditoría; reintentar supone que el fallo puede desaparecer. Para despliegues, prepará rollback o corrección hacia adelante y monitoreá resultados de negocio además del estado verde del pipeline.
