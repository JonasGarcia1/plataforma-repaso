# Timeouts, retries y circuit breakers

## Concepto

Toda llamada remota necesita un timeout que sea menor que el presupuesto total de la operación. Sin él, los hilos pueden esperar hasta agotar recursos. Un retry tiene sentido para fallos transitorios y operaciones idempotentes; un backoff con límite evita concentrar tráfico sobre una dependencia caída.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

Un circuit breaker abre después de una tasa de fallos definida y rechaza rápido mientras la dependencia se recupera. Un bulkhead limita concurrencia o conexiones para que una integración lenta no consuma todos los recursos del proceso. Son mecanismos distintos y deben medirse.

```yaml
# Fragmento de política: los valores se ajustan al presupuesto de la operación.
resilience4j:
  retry:
    instances:
      inventario: { max-attempts: 3, wait-duration: 200ms }
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

**Pregunta:** ¿Cómo elegirías timeouts y reintentos para una llamada remota?

**Breve:** Pondría un timeout dentro del presupuesto total y reintentaría solo fallos transitorios cuando la operación sea segura para repetir.

**Ampliada:** Usaría un límite de intentos, espera exponencial con jitter y un circuit breaker cuando corresponda. Una creación de pedido necesita idempotencia antes del retry; coordinaría los timeouts de cliente, servicio y dependencia para no agotar hilos.
## Error frecuente

Reintentar 400, una validación de negocio o un pago no idempotente. También es peligroso usar el mismo timeout en todas las capas: los presupuestos deben dejar margen para que el llamador pueda manejar el resultado.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Clasificá errores, definí tiempo máximo, cantidad de intentos y qué respuesta recibe el usuario. Luego instrumentá éxitos, fallos, latencia y rechazos del breaker.

Consigna: Una API de inventario tarda 10 segundos pero el checkout dispone de 2. Proponé una política.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Elegí un timeout inferior a 2 segundos, pocos reintentos solo para errores transitorios y una respuesta degradada o rechazo claro cuando no haya stock confirmado. Limitá llamadas concurrentes y registrá la causa.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

La resiliencia no evita fallos: evita que un fallo local se propague sin control. Una política sin métricas es difícil de ajustar y puede ocultar daño.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
