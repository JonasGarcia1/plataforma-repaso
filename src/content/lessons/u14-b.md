## Concepto

DDD, diseño guiado por el dominio, organiza el software alrededor de conceptos y reglas del negocio. El lenguaje ubicuo busca que especialistas y desarrolladores usen palabras con el mismo significado dentro de un contexto.

Una entidad conserva identidad aunque cambien sus atributos. Un value object se define por sus valores, suele ser inmutable y valida invariantes. Un agregado reúne objetos que deben mantener ciertas reglas de forma consistente; su raíz controla las modificaciones.

Un bounded context delimita un modelo y su lenguaje. Cliente puede significar comprador en Ventas y destinatario en Envíos. Obligar a todos a compartir una única clase gigantesca genera acoplamiento. Un contexto no exige automáticamente un microservicio.

## Ejemplo

Fragmento parcial Java 21; value object sin dependencia de persistencia:

```java
record Cantidad(int valor) {
    Cantidad {
        if (valor <= 0) {
            throw new IllegalArgumentException("Cantidad positiva");
        }
    }
}

class Pedido {
    private final UUID id;
    private boolean enviado;

    Pedido(UUID id) { this.id = Objects.requireNonNull(id); }

    void cancelar() {
        if (enviado) throw new IllegalStateException("Ya enviado");
        // Aplicar transición de estado válida.
    }
}
```

Cantidad invalida estados imposibles desde su creación. Pedido tiene identidad y controla una regla; el ejemplo omite su máquina de estados completa.

## En entrevista

**Pregunta:** ¿Cómo se complementan DDD y arquitectura hexagonal?

**Breve:** DDD ayuda a modelar reglas y límites; hexagonal organiza la relación de ese modelo con tecnologías.

**Ampliada:** elegiría agregados pequeños basados en invariantes transaccionales. Entre agregados definiría coordinación explícita y evitaría cargar un grafo completo solo porque existe una relación en la base.
## Error frecuente

Llamar DDD a cualquier proyecto con entidades JPA, o tratar una tabla como agregado sin analizar reglas de negocio.

## Práctica

Un pedido no permite líneas con cantidad cero y no puede cancelarse tras el envío. Ubicá ambas reglas y explicá qué debería hacer un controller.

### Pista

La API puede cambiar y las reglas deben seguir siendo válidas.

### Solución

Cantidad valida el valor positivo; la raíz Pedido controla la transición de cancelación. El controller valida formato, convierte DTOs y llama al caso de uso, sin convertirse en el único guardián de esas invariantes.

## Profundización

Un evento de dominio expresa un hecho pasado del modelo, como PedidoConfirmado. Su publicación externa necesita un contrato estable y una estrategia de entrega; serializar la entidad completa expone detalles internos. DDD aporta más valor donde existe complejidad de negocio que en CRUD trivial.
