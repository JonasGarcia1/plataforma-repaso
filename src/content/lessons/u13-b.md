## Concepto

Un log registra un hecho del sistema con contexto suficiente para investigarlo. DEBUG ayuda al diagnóstico detallado, INFO describe eventos normales relevantes, WARN indica una anomalía recuperable y ERROR un fallo que requiere atención. El nivel depende del impacto, no del gusto del desarrollador.

SLF4J es una fachada: el código usa una API y una implementación escribe los mensajes. Log4j2 y Logback son implementaciones posibles. Boot 3 suele incluir Logback mediante sus starters; usar Log4j2 exige sustituir dependencias de logging de forma coherente.

Los registros estructurados facilitan búsquedas por campos. Un identificador de pedido o correlación conecta eventos, pero no debemos registrar passwords, tokens o cuerpos sensibles. Cada error debería registrarse en el límite adecuado sin repetirse en todas las capas.

## Ejemplo

Fragmento parcial Java 21 con SLF4J; dentro de un servicio de pedidos:

```java
private static final Logger log =
    LoggerFactory.getLogger(PedidoService.class);

void registrarResultado(String pedidoId, int cantidad) {
    log.info("Pedido creado id={} cantidad={}", pedidoId, cantidad);
}

void registrarFallo(String pedidoId, RuntimeException error) {
    log.error("No se pudo procesar pedido id={}", pedidoId, error);
}
```

Los placeholders evitan concatenaciones innecesarias; la excepción final conserva stack trace. El mensaje no incluye email, token ni datos de pago.

## En entrevista

**Pregunta:** ¿Qué información debería aportar un log sin exponer datos sensibles?

**Breve:** logging registra eventos y contexto; SLF4J desacopla la API de la implementación.

**Ampliada:** acordaría niveles, campos, retención y protección de datos. Correlacionaría pedidos con trazas y usaría métricas para alertar: revisar manualmente miles de líneas no escala.
## Error frecuente

Escribir solamente error.getMessage(), perdiendo stack trace, o capturar una excepción solo para registrarla y volver a registrarla más arriba.

## Práctica

Un intento contra catálogo devuelve timeout y luego el reintento tiene éxito. ¿Qué registrarías para evitar una falsa avalancha de errores?

### Pista

Distinguí fallo de intento y resultado final de la operación.

### Solución

Registrar intento fallido con contexto y nivel acordado, más una métrica de reintentos. ERROR puede reservarse para la operación finalmente fallida. Mantener el mismo identificador de correlación y no registrar el token usado para llamar al catálogo.

## Profundización

MDC adjunta contexto al hilo, pero en ejecutores o flujos asíncronos la propagación requiere soporte explícito. Limpiá el contexto al terminar. Configurá rotación, límites y una implementación mantenida; los logs también consumen disco y pueden contener datos personales.
