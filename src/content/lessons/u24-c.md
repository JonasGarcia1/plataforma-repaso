# Caché y decisiones medibles

## Concepto

Cache-aside consulta la caché primero, carga desde la fuente ante un miss y guarda el resultado con una política de expiración. La decisión no termina con un TTL: debe definir clave, tamaño, invalidación, dato tolerablemente viejo y qué sucede si la caché no está disponible.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

Un cache stampede ocurre cuando muchas solicitudes vencidas consultan la fuente al mismo tiempo. Se mitiga con expiración con dispersión, bloqueo por clave o recálculo anticipado según costo. Redis puede acelerar lecturas, pero no transforma un dato en consistente por arte de magia.

```java
// Cache-aside simplificado: definir TTL, invalidación y comportamiento ante fallo.
Producto obtener(String id) {
  return cache.get(id).orElseGet(() -> {
    Producto producto = repositorio.buscar(id);
    cache.put(id, producto);
    return producto;
  });
}
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

**Pregunta:** ¿Cómo controlarías la obsolescencia y el crecimiento de una caché Redis?

**Breve:** Definiría claves, TTL, tamaño máximo y una estrategia de invalidación según cuánto retraso de datos tolere el caso.

**Ampliada:** En cache-aside, una lectura ausente consulta la fuente y carga la caché con expiración. Invalidaría o actualizaría al cambiar el dato, vigilaría tasa de aciertos y memoria, y evitaría guardar información sensible sin controles.
## Error frecuente

Cachear sin saber qué consulta es lenta, o invalidar globalmente ante cada cambio. También es frecuente guardar objetos sin versión ni serialización estable y después no poder evolucionar la representación.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Medí hit ratio, latencia, errores y tamaño antes y después. Si una lectura requiere frescura inmediata, quizá no es candidata; si admite segundos de retraso, declaralo en el contrato.

Consigna: Diseñá caché para un catálogo que cambia pocas veces al día y recibe muchas lecturas.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Usá una clave versionada por producto, TTL razonable y una invalidación al publicar el cambio. Ante caída de Redis, consultá la fuente con límites. Agregá dispersión de expiración para reducir picos simultáneos.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

La caché es una decisión de consistencia y operación. Su éxito se verifica con métricas y con un plan para misses, fallos e invalidación.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
