## Concepto

La arquitectura es una elección entre costos. Un monolito modular se despliega como una unidad pero conserva límites internos claros. Los microservicios agregan despliegue y operación independientes a cambio de comunicación remota, consistencia distribuida y más observabilidad.

No existe equivalencia entre cantidad de servicios y madurez técnica. Si un cambio requiere desplegar cinco servicios coordinadamente y todos escriben en las mismas tablas, la independencia puede ser ilusoria. Un equipo pequeño suele beneficiarse de reducir componentes operativos hasta que exista una necesidad concreta.

Una API Gateway centraliza entrada, enrutamiento y algunas políticas transversales. No debe absorber todo el negocio. Compartir una librería de utilidades puede ayudar; compartir modelos internos entre todos los servicios puede impedir evolucionarlos por separado.

## Ejemplo

Diagrama textual conceptual:

```text
Monolito modular:
HTTP -> módulo Pedidos -> interfaz de Inventario
                  una aplicación, límites verificables

Servicios independientes:
Gateway -> Pedidos --HTTP/eventos--> Inventario
              BD propia                  BD propia
```

En el segundo diseño, una operación remota puede fallar, repetirse o llegar tarde. Esa diferencia afecta las reglas de negocio, no solo la infraestructura.

## En entrevista

**Breve:** elegiría la menor complejidad que satisfaga autonomía, escala y cambios esperados.

**Ampliada:** preguntaría por equipos, frecuencia de despliegue, carga, límites de datos y tolerancia a fallos. Registraría la decisión con contexto, alternativas, consecuencias y señales para revisarla.

## Error frecuente

Dividir un CRUD en microservicios por tabla o prometer transacciones ACID globales porque cada servicio usa @Transactional.

## Práctica

Tres desarrolladores mantienen pedidos e inventario con tráfico moderado y despliegue semanal. ¿Qué arquitectura inicial propondrías y cuándo la revisarías?

### Pista

Evaluá autonomía necesaria y costo operativo, además de escalabilidad.

### Solución

Propondría monolito modular con contratos internos, propiedad de datos y pruebas de límites. Revisaría extracción si un módulo necesitara escala, disponibilidad o ritmo de entrega independiente que compensara el costo distribuido.

## Profundización

El laboratorio springboot-kafka-order-events-lab ilustra separación de pedidos, inventario y notificaciones. Es una herramienta pedagógica con memoria local y un broker, no una demostración de disponibilidad productiva. Para extraer un módulo real, planificá migración de datos, compatibilidad de contratos, monitoreo y reversión del despliegue.
