# Tiempo y entradas robustas

## Concepto

Instant representa un momento en la línea temporal; LocalDate representa una fecha sin hora; LocalDateTime no contiene zona. Elegir el tipo correcto evita desplazar una fecha de negocio por convertirla accidentalmente a UTC. Un Clock inyectable hace comprobable la lógica que depende de “ahora”.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

Validar en el límite no reemplaza las invariantes de negocio. Un controller puede rechazar texto vacío, tamaño excesivo o formato inválido; el dominio todavía debe decidir si el pedido es confirmable. Los límites de longitud, colección y tiempo protegen memoria y dependencias posteriores.

```java
record Pago(String id, Instant confirmadoEn) {}
LocalDate cumpleanios = LocalDate.of(1995, 8, 12);
ZonedDateTime turno = ZonedDateTime.of(2026, 9, 18, 9, 0, 0, 0, ZoneId.of("America/Argentina/Buenos_Aires"));
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

**Pregunta:** ¿Cuándo modelarías un dato como `Instant`, `LocalDate` o `LocalDateTime`?

**Breve:** Usaría `Instant` para un momento global, `LocalDate` para una fecha de calendario y `LocalDateTime` solo cuando la zona no forma parte del dato.

**Ampliada:** Un vencimiento técnico suele guardarse como `Instant`; un cumpleaños como `LocalDate`. Para una reunión local, conservaría la zona horaria junto con la hora, porque `LocalDateTime` por sí solo no identifica un instante único.
## Error frecuente

Usar LocalDateTime para un evento global sin acordar zona, o aceptar null como una ausencia sin definir qué significa. También es riesgoso construir rutas de archivos o consultas a partir de texto no validado.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Definí contrato de entrada, tipo temporal y respuesta de error antes de implementar. En una entrevista, explicá qué dato representa cada tipo y qué zona aplica a presentación, no solo a almacenamiento.

Consigna: Elegí tipos para fecha de cumpleaños, instante de pago y turno de una sucursal de Buenos Aires.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Usá LocalDate para cumpleaños, Instant para pago y un tipo local con ZoneId acordada para el turno. Validá cada campo en su frontera y transformá a Instant solo cuando el significado lo requiera.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

La robustez aparece al modelar ausencia, tamaño y zona con intención. No se resuelve agregando null checks sin una regla de negocio.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
