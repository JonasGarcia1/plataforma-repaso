## Concepto

Una prueba unitaria verifica una conducta acotada con dependencias controladas. JUnit ofrece ejecución, aserciones y organización; Mockito crea dobles de prueba. Un mock no demuestra que la base, HTTP o Kafka funcionen: esos límites requieren pruebas de integración.

La secuencia arrange, act, assert separa preparación, acción y comprobación. TDD propone escribir una prueba que falle por la conducta ausente, implementar lo mínimo y refactorizar manteniendo las pruebas verdes. Cobertura indica código ejecutado, no calidad de aserciones.

Mockito también permite mocks estáticos con su mecanismo compatible. Deben mantenerse acotados y cerrarse; frecuentemente conviene inyectar una dependencia como Clock en vez de reemplazar una función global. MockServer simula un servidor HTTP real para probar nuestro cliente, incluidos estados y demoras.

## Ejemplo

Fragmento parcial Java 21 / JUnit Jupiter y Mockito; Inventario y Pedidos son clases de aplicación:

```java
@Test
void rechazaPedidoSinStock() {
    Inventario inventario = mock(Inventario.class);
    when(inventario.disponible("BOOK-42")).thenReturn(false);
    Pedidos pedidos = new Pedidos(inventario);

    assertThrows(SinStockException.class,
        () -> pedidos.crear("BOOK-42", 1));
    verify(inventario).disponible("BOOK-42");
}

// Mock estático acotado: Ids es una utilidad propia.
try (MockedStatic<Ids> ids = mockStatic(Ids.class)) {
    ids.when(Ids::nuevo).thenReturn("pedido-42");
    assertEquals("pedido-42", Ids.nuevo());
}
```

La segunda muestra es una demostración de API, no una prueba de negocio útil por sí sola.

## En entrevista

**Pregunta:** ¿Qué valida una prueba unitaria con Mockito y qué requiere una integración?

**Breve:** pruebo resultados y reglas; uso mocks para controlar colaboradores, no para simular todo el sistema.

**Ampliada:** combinaría muchas pruebas rápidas con integraciones selectivas de persistencia, serialización y clientes externos. Para HTTP probaría respuestas 200, 500, timeout y cuerpo inválido con MockServer.
## Error frecuente

Tener 100 % de cobertura sin comprobar resultados, o verificar detalles internos que cambian con cualquier refactor.

## Práctica

Diseñá tres pruebas para reservar stock y una integración con un proveedor HTTP de catálogo.

### Pista

Incluí límites y fallos, además del caso exitoso.

### Solución

Reserva válida descuenta exactamente la cantidad; stock insuficiente no modifica nada; cantidad cero es rechazada. En integración, MockServer devuelve 503 y el cliente debe convertirlo en un error controlado sin quedarse esperando indefinidamente.

## Profundización

Separá pruebas de dominio, slices como @WebMvcTest o @DataJpaTest y pruebas completas con @SpringBootTest. Un test que levanta todo no es automáticamente mejor. Probá el motor real cuando la compatibilidad SQL sea parte de lo que querés demostrar.
