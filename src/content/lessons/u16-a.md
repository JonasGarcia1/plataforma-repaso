## Concepto

Autenticación verifica quién actúa; autorización decide qué puede hacer. Spring Security integra filtros y reglas de seguridad, pero la aplicación debe comprobar también permisos sobre recursos concretos: estar autenticado no autoriza a leer cualquier pedido.

OAuth2 es un marco de autorización delegada. JWT es un formato de token, no un protocolo de login ni sinónimo de OAuth2. Un JWT firmado permite verificar integridad, pero su contenido no queda cifrado por defecto. Hay que validar firma, emisor, audiencia y vencimiento según el contrato.

CORS controla qué respuestas puede leer JavaScript de otros orígenes en el navegador; no sustituye autenticación. CSRF aprovecha credenciales enviadas automáticamente por el navegador. Deshabilitar su protección exige analizar el mecanismo real de autenticación, no solo llamar REST a la aplicación.

## Ejemplo

Fragmento parcial Java 21 / Spring Security 6; requiere Resource Server y JWT decoder configurados:

```java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/public/**").permitAll()
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth -> oauth.jwt(
            Customizer.withDefaults()))
        .build();
}
```

El fragmento conserva protección CSRF predeterminada; no es una configuración completa para toda topología. Los permisos del dueño del pedido requieren una comprobación adicional.

## En entrevista

**Pregunta:** ¿Qué diferencia hay entre autenticación y autorización en una API?

**Breve:** separo identidad, permisos y protección del transporte; un token válido no concede acceso universal.

**Ampliada:** usaría HTTPS, permisos mínimos, validación del token y control por recurso. Evitaría registrar secretos y parametrizaría SQL; los stored procedures con SQL dinámico inseguro también pueden ser vulnerables.
## Error frecuente

Decodificar JWT y confiar en sus claims sin verificar firma, o usar CORS como barrera frente a clientes que no son navegadores.

## Práctica

Ana cambia /orders/42 por /orders/43 y ve el pedido de Bruno. ¿Qué falta aunque el JWT sea válido?

### Pista

La identidad está comprobada; el acceso al objeto no.

### Solución

Verificar propiedad o permiso explícito sobre el pedido solicitado en el servicio o política de autorización. Probar usuarios distintos, roles y recursos inexistentes. La API puede elegir 403 o 404 según su contrato y exposición de información.

## Profundización

Revisá revocación, duración y almacenamiento de tokens según riesgo. Una API con cookies y una con bearer token enviado explícitamente no tienen idéntica superficie CSRF. Limitá intentos y tamaños, validá entradas y tratá seguridad como comportamiento verificable.
