## Concepto

SOLID es una guía para que el código cambie con menos sorpresas. No obliga a crear una interfaz por clase. Usalo para detectar una responsabilidad mezclada, un contrato engañoso o una dependencia que hace difícil probar una regla.

- **SRP:** una clase debería cambiar por una razón principal.
- **OCP:** agregá una variación prevista sin reescribir al consumidor cada vez.
- **LSP:** un reemplazo debe respetar el contrato esperado.
- **ISP:** nadie debería depender de métodos que no necesita.
- **DIP:** la regla de negocio depende de un contrato, no de una base o proveedor concreto.

La pregunta útil no es “¿apliqué SOLID?”, sino “¿qué cambio será más fácil y qué acoplamiento saqué?”.

## Ejemplo

Java 21; cada fragmento muestra una mejora pequeña.

```java
// SRP: cálculo y aviso cambian por razones distintas.
record Pedido(int unidades, int precio) {
    int total() { return unidades * precio; }
}

// OCP + DIP: el caso de uso recibe una variación como contrato.
interface Avisos { void enviar(String texto); }
record Confirmar(Avisos avisos) {
    void pedido(Pedido pedido) { avisos.enviar("Total: " + pedido.total()); }
}

// ISP: leer no obliga a poder borrar.
interface ConsultaCatalogo { String buscar(long id); }
```

Si un `ArchivoSoloLectura` hereda `escribir()` y lanza excepción siempre, el contrato ya era demasiado amplio: separá capacidades en lugar de forzar ese subtipo.

## En entrevista

**Respuesta breve:** SOLID ayuda a mantener responsabilidades claras, contratos pequeños y dependencias reemplazables.

**Respuesta ampliada:** daría un problema real: un servicio calcula, guarda y envía correo. Primero separaría esas colaboraciones y pondría la notificación detrás de un contrato. No propondría capas extras si el cambio no las justifica.

## Error frecuente

Confundir SOLID con muchas clases. Una interfaz innecesaria aumenta la superficie a mantener; primero buscá una variación o dependencia concreta que necesite aislarse.

## Práctica

Un servicio valida un pedido, construye SQL y manda correos. ¿Cuál separación harías primero?

### Pista

Elegí partes que cambian por razones diferentes.

### Solución

Conservaría el caso de uso como coordinador y extraería persistencia y avisos detrás de contratos pequeños. Probaría primero las validaciones y los resultados observables para poder reorganizar sin cambiar el comportamiento.

## Profundización

Refactorizar cambia estructura y conserva comportamiento observable. Nombres claros, pruebas relevantes y cambios pequeños suelen aportar más que perseguir siglas.
