## Concepto

`Comparable<T>` define un orden natural dentro del tipo mediante `compareTo`. `Comparator<T>` define un criterio externo mediante `compare`, útil cuando hay varias formas de ordenar pedidos. El resultado es negativo, cero o positivo; no tiene que ser exactamente -1 o 1.

Un criterio debe ser consistente y transitivo. Para ordenar por monto y luego por identificador, componé comparadores: eso hace explícito el desempate. Evitá restar enteros para compararlos porque la resta puede desbordar. `Integer.compare`, `Long.compare` y las funciones `comparing...` expresan mejor la intención.

`equals` define igualdad lógica; `hashCode` debe coincidir para objetos iguales. Dos objetos diferentes pueden compartir hash: una colisión no demuestra igualdad. Una clave cuyo estado usado por `equals/hashCode` cambia mientras está en un `HashMap` puede dejar de ser localizable por búsqueda normal. Por eso son preferibles claves estables.

## Ejemplo

Java 21 ejecutable como `OrdenPedidos.java`:

```java
import java.util.*;
class OrdenPedidos {
    record Pedido(long id, int centavos) {}
    public static void main(String[] args) {
        var pedidos = new ArrayList<>(List.of(
            new Pedido(3, 500), new Pedido(1, 500),
            new Pedido(2, 200)));
        Comparator<Pedido> porMontoEId =
            Comparator.comparingInt(Pedido::centavos)
                      .thenComparingLong(Pedido::id);
        pedidos.sort(porMontoEId);
        System.out.println(pedidos); // ids: 2, 1, 3
        System.out.println(new Pedido(1, 500).equals(new Pedido(1, 500)));
    }
}
```

El record genera igualdad y hash a partir de sus componentes. En un modelo real, decidí si la igualdad de Pedido debe depender solamente del identificador; no la delegues a una herramienta sin revisar su significado.

## En entrevista

**Pregunta:** ¿Qué diferencia hay entre `Comparable` y `Comparator`?

**Breve:** Comparable expresa el orden natural; Comparator permite criterios alternativos y composición. Igualdad y orden son contratos distintos.

**Ampliada:** `TreeSet` determina duplicados según comparación igual a cero. Si comparo solamente el monto, dos pedidos diferentes de 500 se consideran equivalentes para ese conjunto. Para una lista eso es un empate; para un set puede significar perder un elemento esperado.
## Error frecuente

Pensar que `hashCode` debe ser único o que un `TreeSet` usa primero `equals` para decidir si agrega un elemento. También es incorrecto invertir todo el comparador cuando solamente querías invertir el primer criterio.

## Práctica

Ordená por monto descendente y, si empatan, identificador ascendente. ¿Cuántos pedidos conservaría un TreeSet que compara solo monto?

### Pista

Aplicá `reversed()` antes de agregar el desempate.

### Solución

`Comparator.comparingInt(Pedido::centavos).reversed().thenComparingLong(Pedido::id)` produce ids 1, 3, 2. El TreeSet por monto conservaría dos elementos, porque ambos pedidos de 500 comparan como cero. El criterio completo del ejemplo distingue los tres.

## Profundización

Para admitir nombres ausentes, podés envolver un criterio con `nullsFirst` o `nullsLast`. Documentá esa decisión. El orden estable de una lista conserva el orden previo entre empates; no inventa un desempate de negocio.
