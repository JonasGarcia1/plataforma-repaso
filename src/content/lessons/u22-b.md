# GC, mutabilidad y copias defensivas

## Concepto

El garbage collector recupera memoria de objetos inalcanzables. Una fuga ocurre cuando el programa retiene objetos que ya no necesita, por ejemplo mediante una caché sin TTL o una lista estática que nunca se limpia. Aumentar el heap puede retrasar el síntoma sin corregir la retención.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

La mutabilidad compartida multiplica caminos de cambio. Si una clase recibe una lista y la guarda directamente, el llamador puede modificar sus invariantes luego de construirla. Una copia defensiva con List.copyOf expresa que la colección publicada no debe ser modificada desde afuera.

```java
public final class Carrito {
  private final List<String> items;
  public Carrito(List<String> items) { this.items = List.copyOf(items); }
  public List<String> items() { return items; }
}
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

Una respuesta breve sería: “alcanzabilidad, colecciones y límites de estado se usa para tomar una decisión explícita y verificable; primero aclaro el contrato, luego indico el costo y finalmente describo qué haría ante un fallo o un dato inesperado”. Una respuesta ampliada debe sumar un ejemplo concreto, una alternativa descartada y el límite que evita prometer garantías que la herramienta no ofrece.

## Error frecuente

Usar final como sinónimo de inmutable. Final fija la referencia, no el contenido de una lista. También es erróneo llamar al GC manualmente como mecanismo de corrección de una fuga.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Elegí inmutabilidad por defecto para valores pequeños y documentá claramente las operaciones que cambian estado. Medí memoria y referencias retenidas antes de culpar al recolector.

Consigna: Modelá un pedido que no permita que su lista de líneas sea modificada por código externo.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Copiá la entrada al construir y devolvé una vista inmodificable o una copia. Para agregar una línea, exponé una operación que valide cantidad y actualice el estado bajo control de la clase.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

La copia defensiva es una frontera de diseño. En datos grandes puede tener costo, por lo que se evalúa el contrato, el volumen y la propiedad del dato.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
