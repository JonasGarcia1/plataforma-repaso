# APIs que pueden evolucionar

## Concepto

Una API de lectura necesita definir orden estable, tamaño máximo y significado de filtros. Offset es sencillo, pero puede saltar o repetir elementos si los datos cambian entre páginas. Un cursor basado en el último orden conocido suele ser más estable en recorridos grandes, siempre que el orden y la clave de desempate formen parte del contrato.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

Versionar no significa agregar /v2 ante cualquier ajuste. Primero se evalúa si el cambio es aditivo y compatible. Quitar un campo, cambiar su significado o modificar una regla de validación puede romper clientes aunque la ruta no cambie. La documentación y ejemplos son parte del contrato.

```java
// Fragmento Spring MVC: cursor opaco y orden estable son parte del contrato.
@GetMapping("/pedidos")
PaginaPedido listar(@RequestParam Optional<String> cursor,
                    @RequestParam(defaultValue = "20") int limite) { return servicio.listar(cursor, limite); }
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

Una respuesta breve sería: “paginación, filtros y compatibilidad se usa para tomar una decisión explícita y verificable; primero aclaro el contrato, luego indico el costo y finalmente describo qué haría ante un fallo o un dato inesperado”. Una respuesta ampliada debe sumar un ejemplo concreto, una alternativa descartada y el límite que evita prometer garantías que la herramienta no ofrece.

## Error frecuente

Devolver una lista sin límites o paginar sin ORDER BY. También es un error aceptar filtros ambiguos que no declaran zona temporal, formato, valores permitidos o comportamiento frente a campos desconocidos.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Diseñá primero la representación de la consulta y de sus enlaces o cursor. Después agregá métricas para saber si los clientes recorren demasiadas páginas o usan combinaciones costosas.

Consigna: Diseñá GET /pedidos con estado, fecha y cursor. Indicá qué orden garantizás.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Definí un orden por fecha de creación e id como desempate, limitá tamaño, devolvé el siguiente cursor solo si existe más resultado y documentá que el cursor no se interpreta como dato de negocio.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

Una API evoluciona mejor con contratos explícitos, pruebas de compatibilidad y un período de transición. La versión de URL es una herramienta, no la estrategia completa.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
