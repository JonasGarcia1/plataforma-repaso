## Concepto

OpenAPI describe una API HTTP: rutas, operaciones, parámetros, esquemas, respuestas y mecanismos de seguridad. Puede escribirse en YAML o JSON. Swagger es un conjunto de herramientas relacionadas, entre ellas Swagger UI; YAML no es un lenguaje exclusivo de Swagger.

Postman permite organizar peticiones en colecciones, usar variables de entorno y comprobar respuestas. Las colecciones ayudan a explorar y automatizar ejemplos, pero no reemplazan las pruebas de negocio. Una documentación navegable tampoco garantiza que el servidor cumpla su contrato.

Diseñar una API requiere decidir paginación, filtros, validación y compatibilidad. Nombres de recursos estables y errores coherentes ahorran sorpresas. Agregar un campo opcional suele ser menos disruptivo que renombrar uno obligatorio, aunque clientes estrictos también pueden requerir pruebas de compatibilidad.

## Ejemplo

Fragmento parcial OpenAPI 3.0 en YAML; describe una operación mínima:

```yaml
openapi: 3.0.3
info:
  title: Pedidos
  version: 1.0.0
paths:
  /api/orders/{id}:
    get:
      parameters:
        - in: path
          name: id
          required: true
          schema:
            type: integer
      responses:
        '200':
          description: Pedido encontrado
        '404':
          description: Pedido inexistente
```

Un contrato completo agregaría schemas de respuesta, ejemplos y seguridad cuando aplique. En Boot 3 se puede integrar springdoc compatible con esa generación.

## En entrevista

**Pregunta:** ¿Qué diferencia hay entre OpenAPI, Swagger UI y Postman?

**Breve:** OpenAPI es la especificación; Swagger UI la presenta de forma interactiva; Postman ejecuta solicitudes.

**Ampliada:** validaría que ejemplos, estados y esquemas coincidan con el comportamiento. Exportaría colecciones sin credenciales y usaría entornos para cambiar la URL base.
## Error frecuente

Compartir un token real dentro de una colección, o documentar solo el caso exitoso dejando al consumidor sin contrato de errores.

## Práctica

Prepará una colección conceptual para crear un pedido y consultarlo. ¿Qué datos y comprobaciones pasan entre ambas solicitudes?

### Pista

La primera respuesta debe comunicar la identidad creada.

### Solución

Guardar id o Location del POST, comprobar 201, hacer GET con esa identidad y comprobar 200, sku y cantidad. Agregar una cantidad inválida con 400 y una identidad ausente con 404.
