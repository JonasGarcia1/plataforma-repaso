## Concepto

Una caché guarda resultados reutilizables para reducir latencia y carga. En cache-aside la aplicación consulta caché, lee la fuente si falta y guarda el resultado con vencimiento. Redis permite compartir esa caché entre instancias; un mapa local no comparte estado ni sobrevive necesariamente a reinicios.

La decisión principal es cuánto dato desactualizado tolera el negocio. Un catálogo descriptivo puede tolerar minutos; el stock para autorizar una compra suele necesitar una verificación fuerte. TTL, invalidación y política ante caída de caché deben ser explícitos.

Para rendimiento, medimos antes de cambiar. La JVM administra heap y garbage collection; también importan memoria nativa, hilos, CPU, pools y SQL. Un heap mayor no arregla una fuga ni una consulta lenta. JFR y herramientas de diagnóstico ayudan a encontrar asignaciones, bloqueos y esperas.

## Ejemplo

Pseudocódigo Java para catálogo; las interfaces representan adaptadores y no una API concreta de Redis:

```java
Catalogo obtener(String categoria) {
    Catalogo guardado = cache.leer(categoria);
    if (guardado != null) return guardado;

    Catalogo actual = repositorio.buscar(categoria);
    cache.guardar(categoria, actual, Duration.ofMinutes(5));
    return actual;
}
```

Faltan deliberadamente manejo de indisponibilidad, coordinación de recargas e invalidación. Los cinco minutos son una decisión de ejemplo, no una recomendación universal.

## En entrevista

**Pregunta:** ¿Qué decisiones hay que tomar al implementar cache-aside con Redis?

**Breve:** agrego caché cuando conozco el costo de la lectura y la tolerancia a desactualización.

**Ampliada:** definiría claves, TTL, tamaño máximo y métricas hit/miss. Controlaría estampidas mediante recarga coordinada, límites y expiraciones con variación. Ante caída de Redis protegería la base contra una avalancha de lecturas.
## Error frecuente

Cachear stock como única autoridad de compra o creer que un circuit breaker reintenta automáticamente. El breaker frena llamadas ante fallos; el retry vuelve a intentarlas.

## Práctica

Un catálogo cambia una vez al día y recibe miles de lecturas. Proponé caché e indicá tres casos límite.

### Pista

Considerá dato ausente, actualización y pérdida de la caché.

### Solución

Cache-aside con TTL acordado e invalidación al actualizar. Distinguir catálogo vacío de error; limitar carga concurrente tras expiración; permitir lectura de fuente solo dentro de su capacidad cuando Redis falle. Medir aciertos y latencia.

## Profundización

Usá timeouts por dependencia y un presupuesto total; combiná retries limitados con jitter solo para operaciones seguras. Ante pausas largas inspeccioná GC y asignaciones. Ante latencia sin CPU alta revisá esperas de red, locks y pool antes de sumar hilos.
