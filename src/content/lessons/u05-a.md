## Concepto

Una excepción interrumpe el flujo normal hasta encontrar un manejador compatible. `throw` lanza una instancia; `throws` declara excepciones que un método puede propagar. Las checked, como `IOException`, deben capturarse o declararse. Las subclases de `RuntimeException` son unchecked; no requieren esa declaración. `Error` suele representar fallos graves que no conviene tratar como errores normales del negocio.

Elegí dónde hay información suficiente para actuar. Un importador puede agregar contexto al fallo de lectura; una capa superior decide si muestra un mensaje, cancela o reintenta. Capturar todo y seguir como si nada convierte un fallo visible en datos incorrectos.

Una excepción propia comunica intención cuando los tipos existentes no alcanzan. Su mensaje debe ayudar a diagnosticar sin incluir secretos. Si traducís una excepción técnica a otra del dominio o aplicación, preservá la causa original; así no desaparece el lugar donde empezó el problema.

## Ejemplo

Java 21, clase completa compilable; requiere un archivo al invocar el método:

```java
import java.io.IOException;
import java.nio.file.*;
class Importador {
    static class ImportacionFallida extends RuntimeException {
        ImportacionFallida(String mensaje, Throwable causa) {
            super(mensaje, causa);
        }
    }
    static String leer(Path archivo) {
        try {
            return Files.readString(archivo);
        } catch (IOException causa) {
            throw new ImportacionFallida("No se pudo leer el catálogo", causa);
        }
    }
}
```

Esta traducción es una decisión de frontera. No significa que todas las checked deban convertirse siempre a unchecked.

## En entrevista

**Respuesta breve:** checked obliga a declarar o manejar; unchecked no. Las capturo cuando puedo recuperar o agregar contexto útil.

**Respuesta ampliada:** para una reserva inválida puedo devolver un resultado de negocio o lanzar una excepción del dominio según el contrato. No usaría una excepción por cada elemento ausente de una búsqueda normal. El tipo debe distinguir una situación esperada de una falla inesperada.

## Error frecuente

Registrar el mismo error en cada capa y volver a lanzarlo: genera ruido duplicado. También lo es retornar `null` después de una excepción y obligar a otro componente a fallar sin contexto.

## Práctica

Una lectura falla por permisos. ¿Reintentarías diez veces inmediatamente? ¿Qué información conservarías?

### Pista

Un reintento sirve si la causa puede desaparecer.

### Solución

No repetiría automáticamente un error persistente de permisos. Conservaría causa y operación afectada, sin exponer contenido sensible. Informaría el fallo en la frontera adecuada y permitiría corregir permisos antes de volver a intentar.

## Profundización

En `catch` colocá tipos específicos antes que generales. Las excepciones de interrupción requieren atención especial: si no podés propagarlas, suele corresponder restaurar el flag con `Thread.currentThread().interrupt()` y terminar la operación.
