# Pruebas de integración operables

## Concepto

Un test unitario aísla una regla; una prueba de integración verifica que adaptadores y configuraciones colaboran con una dependencia real. Testcontainers crea servicios efímeros para evitar que una prueba dependa de una base instalada manualmente o de datos que dejó otro test. No reemplaza todos los tests unitarios porque suele ser más lento.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

Graceful shutdown deja de aceptar trabajo nuevo, permite terminar operaciones dentro de un límite y cierra recursos. Es distinto de matar el proceso inmediatamente. En un consumer de mensajes también se considera qué ocurre con la confirmación del offset y qué trabajo puede repetirse.

```java
@Testcontainers
class ClienteRepositoryIT {
  @Container static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16");
  // La prueba usa la URL efímera del contenedor, no una base local compartida.
}
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

Una respuesta breve sería: “Testcontainers, dependencias reales y shutdown se usa para tomar una decisión explícita y verificable; primero aclaro el contrato, luego indico el costo y finalmente describo qué haría ante un fallo o un dato inesperado”. Una respuesta ampliada debe sumar un ejemplo concreto, una alternativa descartada y el límite que evita prometer garantías que la herramienta no ofrece.

## Error frecuente

Usar una base compartida sin limpieza y llamar integración a cualquier prueba que carga el contexto. También es un error asumir que un cierre elegante vuelve atómica una operación distribuida.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Probá una ruta completa que incluya migración, repositorio y contrato HTTP. Hacé que los datos del test sean propios de la prueba y verificá efectos observables, no detalles internos de Spring.

Consigna: Escribí qué cubrirías para confirmar que una migración crea un índice y que GET /clientes responde paginado.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Arrancá una base temporal, aplicá las migraciones, insertá datos del caso y consultá la API. Verificá respuesta, orden y el índice mediante metadatos o plan de consulta, según el objetivo del test.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

Las pruebas de integración son una red de seguridad para las fronteras más riesgosas. Se reservan para comportamientos que un mock no puede demostrar.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
