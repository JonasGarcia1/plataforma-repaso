## Concepto

Java atraviesa un recorrido: escribís un archivo `.java`, el compilador `javac` lo convierte a bytecode `.class` y una JVM compatible lo ejecuta. La JVM administra memoria, carga clases e interpreta o compila código a instrucciones de la máquina mediante JIT. El JDK incluye las herramientas para desarrollar y ejecutar; no es solamente el compilador. JRE nombra el entorno de ejecución, aunque su distribución separada depende del proveedor y la versión.

Maven coordina la construcción a partir del `pom.xml`: identifica el proyecto y sus dependencias por `groupId`, `artifactId` y `version`. Su ciclo incluye `compile`, `test`, `package`, `verify`, `install` y `deploy`. Ejecutar una fase también recorre las anteriores; `clean` pertenece a otro ciclo y borra resultados generados.

Una dependencia `compile` está disponible al compilar y ejecutar. `test` se limita a pruebas; `runtime` se necesita al ejecutar, aunque no al compilar; `provided` la aporta el entorno objetivo. `dependencyManagement` fija versiones y configuración, pero por sí solo no agrega la dependencia. Versiones explícitas y un wrapper ayudan a reproducir la construcción.

## Ejemplo

Fragmento de `pom.xml` para un proyecto configurado con Maven Compiler Plugin compatible:

```xml
<properties>
  <maven.compiler.release>21</maven.compiler.release>
  <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>
```

```shell
java -version
javac -version
./mvnw verify
./mvnw dependency:tree
```

En Windows, el wrapper es `mvnw.cmd`. El árbol de dependencias permite investigar qué biblioteca trae una versión transitiva inesperada.

## En entrevista

**Pregunta:** ¿Qué diferencia hay entre JDK, JVM y bytecode, y dónde entra Maven?

**Breve:** el JDK permite desarrollar; la JVM ejecuta bytecode y Maven automatiza dependencias, pruebas y empaquetado.

**Ampliada:** revisaría versión del compilador, `release`, runtime objetivo y dependencias transitivas. Un proyecto que compila con Java 21 puede producir bytecode para una versión anterior usando `release`, siempre que su código y dependencias sean compatibles.
## Error frecuente

Confundir `install` con instalar la aplicación en producción: publica el artefacto en el repositorio Maven local. `deploy` lo publica en un repositorio de artefactos remoto.

## Práctica

Tu servicio usa JUnit y un driver JDBC que carga en ejecución. Elegí sus scopes y cómo verificarías conflictos de versiones.

### Pista

Pensá quién importa las clases y en qué momento se necesitan.

### Solución

JUnit usa `test`. Un driver usado solamente por carga dinámica puede ser `runtime`; si importás clases del proveedor al compilar, necesitás disponibilidad en compilación. Inspeccioná `dependency:tree` y ejecutá `verify` con el JDK acordado.

## Profundización

Maven selecciona dependencias transitivas por reglas de mediación; una BOM centraliza versiones compatibles. Revisá también plugins y repositorios: fijar solamente versiones de bibliotecas no hace completamente reproducible una construcción.
