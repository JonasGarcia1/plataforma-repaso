# Entorno reproducible y terminal

## Concepto

Un proyecto no debería depender de una configuración secreta de una computadora. El JDK que compila, la versión declarada por Maven y las variables necesarias deben ser visibles y reproducibles. JAVA_HOME identifica una instalación; PATH permite encontrar ejecutables. Ninguna de las dos es un lugar para una contraseña.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

En la terminal, java -version, javac -version y mvn -v muestran qué herramientas se ejecutan de verdad. Si el IDE compila con una versión y la terminal con otra, el problema no es el código: es la discrepancia de entorno. Un README debe decir requisitos y comandos, no asumir rutas personales.

```text
# Comandos de terminal; no incluir secretos en argumentos ni historial.
java -version
javac -version
mvn -v
echo $env:JAVA_HOME       # PowerShell
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

Una respuesta breve sería: “JDK, PATH, variables de entorno y procesos se usa para tomar una decisión explícita y verificable; primero aclaro el contrato, luego indico el costo y finalmente describo qué haría ante un fallo o un dato inesperado”. Una respuesta ampliada debe sumar un ejemplo concreto, una alternativa descartada y el límite que evita prometer garantías que la herramienta no ofrece.

## Error frecuente

Copiar un token en un comando, archivo de propiedades versionado o captura de pantalla. Los secretos se inyectan desde el entorno o un gestor apropiado y se redactan en logs.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Antes de cambiar dependencias, reproducí el fallo con un comando pequeño. Anotá versión, directorio, argumento y salida relevante. Eso convierte una observación vaga en evidencia que otra persona puede repetir.

Consigna: Listá qué verificarías si mvn test usa Java 17 y la aplicación exige Java 21.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Comprobá el JAVA_HOME efectivo, el orden de PATH, la configuración del IDE y el toolchain de Maven. Elegí una única fuente de verdad para el proyecto y documentala sin incluir secretos.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

La terminal no reemplaza al IDE: permite aislar si el fallo pertenece al código, al build o al entorno. Esa separación ahorra tiempo en entrevistas y en incidentes.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
