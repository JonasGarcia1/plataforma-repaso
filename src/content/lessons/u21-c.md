# Stack traces y logs iniciales

## Concepto

Un stack trace describe una cadena de llamadas y, cuando existe, una causa. La primera línea que pertenece a tu código suele ser un buen punto de partida, pero la causa más profunda explica por qué falló. Leer solo la última línea puede llevar a arreglar un síntoma.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

Los logs deben responder qué ocurrió, en qué operación y con qué identificador seguro. INFO cuenta hitos operativos, WARN señala una condición degradada y ERROR registra un fallo que requiere atención. No se registran contraseñas, tokens ni cuerpos completos de datos sensibles.

```java
// Fragmento SLF4J: incluye contexto técnico, nunca token ni datos sensibles.
log.warn("No se pudo reservar pedido={}, causa={}", pedidoId, error.getClass().getSimpleName());
throw new ReservaException("No pudimos confirmar la reserva", error);
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

Una respuesta breve sería: “causas, niveles y contexto seguro se usa para tomar una decisión explícita y verificable; primero aclaro el contrato, luego indico el costo y finalmente describo qué haría ante un fallo o un dato inesperado”. Una respuesta ampliada debe sumar un ejemplo concreto, una alternativa descartada y el límite que evita prometer garantías que la herramienta no ofrece.

## Error frecuente

Registrar cada detalle como ERROR o atrapar una excepción para imprimirla y continuar con estado inválido. El nivel no reemplaza el manejo correcto; el contexto tampoco debe revelar información privada.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Relacioná un stack trace con una solicitud, un pedido o un correlation ID. Esa correlación permite seguir el caso entre capas sin transformar logs en una base de datos de datos personales.

Consigna: Leé una excepción que envuelve SQLException y describí qué parte guardarías en el log.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Conservá tipo de excepción, mensaje seguro, operación, identificador técnico y causa. En la respuesta HTTP devolvé un problema comprensible sin exponer la cadena interna ni la consulta SQL.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

Un log útil permite formular la siguiente pregunta. La observabilidad madura suma métricas y trazas, pero empieza por una causa preservada y contexto mínimo.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
