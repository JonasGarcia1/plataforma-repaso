# Errores, migraciones y preparación

## Concepto

Los errores previsibles deben tener un formato consistente que indique tipo, título, estado y detalle seguro. Problem Details separa el error que un cliente puede corregir de una excepción interna. Un handler global traduce fronteras HTTP; no debe convertir todo en 500 ni ocultar un problema de programación como si fuera validación.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

Una migración versionada describe cómo cambia el esquema. Flyway aplica versiones en orden y registra cuáles se ejecutaron. El cambio debe ser compatible con el despliegue: primero puede agregarse una columna opcional, luego publicar consumidores que la escriban y por último volverla obligatoria.

```java
// Fragmento Spring Boot: la migración vive versionada en db/migration.
@ExceptionHandler(ClienteNoEncontrado.class)
ProblemDetail noEncontrado(ClienteNoEncontrado error) {
  return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, error.getMessage());
}
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

**Pregunta:** ¿Cómo diseñarías errores HTTP consistentes y migraciones de esquema seguras?

**Breve:** Definiría un formato de error estable con estado HTTP y detalle seguro; aplicaría migraciones versionadas y comprobaría salud por separado.

**Ampliada:** Un handler global puede producir Problem Details con un identificador de correlación, sin filtrar excepciones internas. Flyway versiona cambios de esquema; usaría cambios compatibles por etapas si versiones anteriores de la aplicación siguen ejecutándose.
## Error frecuente

Confiar en ddl-auto en producción o usar un health check que solo responde que el proceso está vivo. Liveness indica si reiniciar puede ayudar; readiness indica si una instancia puede recibir tráfico sin fallar dependencias necesarias.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Pensá la migración junto con rollback lógico, datos existentes y orden de despliegue. La observabilidad de readiness evita enviar tráfico a una instancia que arrancó pero todavía no puede operar.

Consigna: Agregá email obligatorio a clientes que ya tienen registros sin email. Proponé una secuencia segura.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Creá primero el campo nullable, desplegá lectura tolerante y escritura del nuevo campo, completá datos existentes, validá y recién entonces imponé NOT NULL. Registrá la versión de esquema aplicada.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

Operar una API requiere saber si está disponible y por qué no. Los endpoints de Actuator ayudan, pero su exposición y datos deben protegerse.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
