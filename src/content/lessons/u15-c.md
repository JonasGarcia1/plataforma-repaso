## Concepto

Una transacción local no abarca automáticamente varios servicios. Si Pedidos confirma y Pagos falla, necesitamos definir qué estado observa el usuario y cómo se recupera el flujo. Consistencia eventual significa que las vistas convergen mediante procesamiento posterior bajo condiciones definidas; no significa aceptar incoherencia indefinida.

Una saga divide una operación en pasos locales y compensaciones. Compensar no siempre restaura exactamente el pasado: reembolsar un pago deja un registro y puede tardar. La coreografía reparte reacciones a eventos; la orquestación centraliza la coordinación del flujo.

Los eventos necesitan contratos que evolucionen. Un campo opcional nuevo suele permitir transición, pero hay que probar consumidores reales. Compartir el mismo objeto de persistencia entre servicios acopla versiones y revela detalles internos.

## Ejemplo

Secuencia conceptual para compra, sin suponer transacción global:

```text
1. Pedidos: crear PENDIENTE.
2. Inventario: reservar stock -> StockReservado.
3. Pagos: cobrar -> PagoConfirmado.
4. Pedidos: marcar CONFIRMADO.

Si el pago es rechazado:
5. Inventario: liberar reserva de forma idempotente.
6. Pedidos: marcar CANCELADO.
```

Si un mensaje se demora, el pedido continúa pendiente y el usuario necesita una respuesta clara. Una compensación también puede fallar y requiere seguimiento.

## En entrevista

**Pregunta:** ¿Cómo modelarías una operación distribuida que puede fallar a mitad de camino?

**Breve:** en sistemas distribuidos diseño estados intermedios, reintentos y compensaciones explícitos.

**Ampliada:** aclararía qué regla exige consistencia inmediata y qué puede converger. Elegiría saga solo cuando el proceso realmente cruza límites transaccionales; no la usaría para complicar una operación que cabe en una transacción local.
## Error frecuente

Prometer que una gateway resuelve consistencia o transacciones. La gateway puede enrutar y aplicar políticas, pero cada servicio conserva sus invariantes y autorización de negocio.

## Práctica

Se confirmó un pago pero se perdió la respuesta. El cliente reintenta. ¿Por qué un timeout no demuestra rechazo y cómo evitarías un segundo cobro?

### Pista

El resultado observado por el cliente puede diferir del estado del proveedor.

### Solución

Un timeout es resultado desconocido. Consultar el estado o reutilizar una clave de idempotencia acordada con el proveedor. No ejecutar un cobro nuevo sin reconciliación. Mantener el pedido pendiente hasta conocer el resultado.

## Profundización

El caso guiado de [dos microservicios con Wikimedia](/leccion/kafka-real-world) muestra cómo separar productor, consumer y proyección sin simular una transacción global.

Definí plazos de procesamiento, reconciliación y alarmas para pedidos atascados. Para eventos, incluí identificador, tipo, versión y datos necesarios sin filtrar secretos. En el laboratorio existente no hay saga ni pago real: estos pasos son una extensión conceptual de su flujo de pedidos.
