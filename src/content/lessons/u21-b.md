# Debugging con una hipótesis

## Concepto

Depurar no es recorrer línea por línea hasta que algo parezca raro. Se parte de un comportamiento observable, una hipótesis y un punto donde la evidencia puede confirmarla o descartarla. Un breakpoint antes de la decisión permite inspeccionar entradas; uno dentro de un loop sirve para observar un invariante, no para leer miles de iteraciones.

Pensalo con un pedido, inventario o notificación: los datos y las dependencias cambian, pero el límite correcto permite comprobar qué parte tomó una decisión. La meta no es memorizar una API, sino explicar el contrato, el costo y el riesgo de la alternativa elegida. Cuando una regla depende de infraestructura, dejá visible qué asume el código y qué debe verificar el entorno.

## Ejemplo

Step over ejecuta la llamada sin entrar; step into sigue su implementación; step out vuelve al llamador. Un watch resulta útil cuando una variable cambia de manera inesperada. La condición de un breakpoint reduce ruido y evita detenerse en cada elemento de una colección grande.

```java
// Pausá aquí cuando cantidad sea 0 o menor y observá stockDisponible.
boolean puedeConfirmar(int cantidad, int stockDisponible) {
  if (cantidad <= 0 || cantidad > stockDisponible) return false;
  return true;
}
```

El fragmento es ilustrativo salvo en la lección de algoritmos, cuyo ejemplo es una clase Java 21 completa. En producción, los nombres, errores y límites se ajustan al contrato del módulo y se prueban con entradas normales y de borde.

## En entrevista

Una respuesta breve sería: “breakpoints, pasos e inspección de estado se usa para tomar una decisión explícita y verificable; primero aclaro el contrato, luego indico el costo y finalmente describo qué haría ante un fallo o un dato inesperado”. Una respuesta ampliada debe sumar un ejemplo concreto, una alternativa descartada y el límite que evita prometer garantías que la herramienta no ofrece.

## Error frecuente

Modificar valores en el debugger para “arreglar” un caso y concluir que la aplicación funciona. Esa modificación puede ocultar la causa. También es un error detenerse dentro de infraestructura sin entender el contrato que se está investigando.

La corrección empieza por observar evidencia: entradas, resultado esperado, dependencia involucrada y métrica o prueba que puede demostrar el cambio. Evitá agregar complejidad si una regla local, un contrato mejor definido o una consulta medida resuelve el problema.

## Práctica

Usá el debugger junto con una prueba reproducible. Guardá el dato de entrada y agregá una aserción una vez encontrada la causa, para que el mismo fallo no dependa de una inspección manual futura.

Consigna: Un pedido acepta stock negativo solo en una ruta. Elegí un breakpoint y una condición de inspección.

### Pista

Escribí primero qué debe mantenerse verdadero mientras avanza el proceso. Enumerá al menos dos casos límite y anotá el tiempo y espacio de la solución antes de implementar. Si interviene una dependencia externa, definí qué ocurre ante timeout, dato inválido o reinicio.

### Solución

Ubicalo en la transición que descuenta stock y verificá cantidad, stock previo y origen de la llamada. Si cantidad ya era negativa al entrar, seguí hacia arriba; si cambia dentro, la regla falta en esa operación.

Comprobá la solución con un caso feliz, un borde y una entrada inválida. Si el resultado afecta otra capa, agregá una aserción en esa frontera en lugar de confiar únicamente en una inspección manual.

## Profundización

El mejor resultado del debugging es una explicación verificable y una prueba. El debugger da observabilidad local; la prueba preserva el aprendizaje.

Relacioná este tema con una lección previa y con una posterior: una buena explicación muestra cómo una decisión local cambia el comportamiento del sistema completo. Documentá la hipótesis, medí el resultado y revisá la decisión cuando cambien los datos o las restricciones.
