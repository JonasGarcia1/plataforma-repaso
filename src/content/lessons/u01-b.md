## Concepto

Git separa tres lugares: archivos de trabajo, índice de preparación y commits. `add` prepara una instantánea; `commit` registra el índice. Una rama es una referencia móvil a un commit. `fetch` actualiza referencias remotas; `pull` además integra cambios según configuración.

Git Flow mantiene `main` para versiones publicadas y `develop` para integración. Las ramas `feature`, `release` y `hotfix` representan trabajo, preparación y correcciones urgentes. Es una convención útil en algunos equipos; despliegues frecuentes también pueden usar ramas cortas sobre una principal.

Una pull request permite revisar intención, implementación y pruebas. Si hay conflicto, identificá el comportamiento esperado, editá la combinación, prepará los archivos y continuá la operación. Que Git pueda unir texto no garantiza que el resultado funcione.

## Ejemplo

Secuencia orientativa, para practicar en un repositorio descartable:

```shell
git switch -c feature/validar-stock
git status
git add src/Inventario.java
git diff --staged
git commit -m "Valida stock antes de reservar"
git fetch origin
git rebase origin/develop
```

| Operación | Efecto y cuidado |
| --- | --- |
| `restore archivo` | Descarta cambios del archivo de trabajo usando el índice. |
| `restore --staged archivo` | Retira cambios del índice, conservando el trabajo. |
| `reset --soft HEAD~1` | Mueve la rama un commit atrás, conserva índice y trabajo. |
| `reset --hard` | Reemplaza índice y trabajo; puede perder cambios locales. |
| `rm archivo` | Elimina el archivo y prepara su eliminación. |
| `commit --amend` | Reemplaza el último commit, incluidos contenido y mensaje. |
| `stash push -u` | Guarda cambios locales e incluye archivos no rastreados. |
| `rebase -i` con squash | Reescribe varios commits como uno. |
| `cherry-pick hash` | Aplica el cambio de un commit y crea otro commit. |

## En entrevista

**Respuesta breve:** uso ramas cortas, commits con intención y revisión antes de integrar; sigo la estrategia del equipo.

**Respuesta ampliada:** merge conserva la historia de las ramas; rebase reaplica commits sobre otra base y cambia sus identificadores. Evito reescribir historia compartida sin coordinación. Para deshacer un commit publicado suelo usar `revert`, que agrega una corrección explícita.

## Error frecuente

Pensar que `.gitignore` deja de rastrear archivos ya versionados. No lo hace; `rm --cached` los retira del índice conservando la copia local.

## Práctica

Preparaste dos archivos pero solo uno debe entrar al commit. Además, detectaste un error en un commit ya compartido. ¿Qué harías?

### Pista

Separá modificar el índice de reescribir historial.

### Solución

Usá `restore --staged` sobre el archivo extra. Para el error publicado, creá una corrección o un `revert`, según quieras arreglar o deshacer todo el cambio. Revisá el diff y probá el resultado antes de publicar.

## Profundización

`reflog` ayuda a encontrar referencias locales anteriores. No reemplaza backups ni garantiza recuperar archivos nunca guardados. Los conflictos se resuelven igual de cuidadosamente en merge, rebase y cherry-pick.
